# אירועי קהילה ואירועים פרטיים חריגים

תיעוד אירועים שאינם הזמנות שבת, לצורך עדכון מלאי וניהול גבייה.

תאריך תכנון: 2026-07-28. **מומש במלואו באותו יום** - ראו "מה נבנה בפועל" בסוף.

---

## 1. ההחלטות שנקבעו

| נושא | ההחלטה |
|---|---|
| היקף תפעולי | ברירת מחדל: מסך קל ונפרד. עם כפתור "הפוך למועד מלא" שפותח את כל מנגנון תיק השבת |
| תפריט האירוע | מאכלים מהקטלוג הקיים **וגם** שורות חופשיות של פריטי מלאי |
| תמחור אירוע פרטי | לפי עלות המוצרים שנצרכו × מספר המנות, עם אפשרות תיקון ידני |
| אירוע פנימי | יש גורם משלם וגבייה, בדיוק כמו לקוח |

מסקנה מהשורה האחרונה: אין הבדל מבני בין "אירוע פנימי" ל"אירוע פרטי". שניהם
אירוע עם משלם וחוב. ההבדל הוא תיוג בלבד (`event_type`), לצורך סינון ודוחות.

---

## 2. עקרון התכנון: אירוע = מועד + הזמנה אחת

זהו הלב של התוכנית, וממנו נגזר כמעט כל השאר.

היום המערכת בנויה סביב שרשרת אחת:

```
shabbatot (מועד)
   └── shabbat_files (תיק עבודה)   ← ניכוי מלאי, מתנדבים, אריזה, שינוע, הדפסות
   └── orders (הזמנה)              ← מנות, מאכלים, תוספות, הנחות, גבייה, החזרים
          └── customer_payments     ← תשלומים, יתרה, סטטוס תשלום
```

**אירוע ייכנס לאותה שרשרת** ולא יבנה שרשרת מקבילה:

```
shabbatot (kind='event')  ← "מועד" מסוג אירוע
   └── shabbat_files       ← נוצר תמיד, אבל מוצג רק ב"מועד מלא"
   └── orders (הזמנה אחת)  ← המשלם, התפריט, הסכום
          └── customer_payments
```

### למה זה נכון כאן

מה שמתקבל בלי לכתוב שורת קוד:

- גבייה מלאה: `customer_payments`, יתרה, `payment_status`, החזרים, היסטוריה.
- דוחות כספיים: `finance.js` שואב מ-`orders` ומ-`customer_payments`, האירוע נכנס מיד.
- ניכוי מלאי אטומי: ה-RPC `deduct_shabbat_inventory` מקבל `shabbat_id` ומשתמש
  ב-`shabbat_files.is_inventory_deducted` כהגנה מפני ניכוי כפול. עובד as-is.
- דוח חוסרים, הזמנת רכש ישירה (`purchase_orders.shabbat_id`), דוח מטבח, מתנדבים,
  הדפסות. כל אלה מפתחים על `shabbat_id` ולכן "מועד מלא" הוא באמת מתג תצוגה בלבד.

החלופה (טבלת `events` נפרדת עם `event_orders`, `event_payments`) הייתה מחייבת
שכפול של כל השרשרת הזו, כולל ה-RPC והדוחות הכספיים. עלות גבוהה בהרבה, ומקור
אמת שני שיסטה מהראשון עם הזמן.

### המחיר של הבחירה

`shabbatot` הופכת סמנטית לטבלת **מועדים**. שני דברים חייבים טיפול:

1. **אינדקס ייחודי על התאריך.** היום `uq_shabbatot_gregorian_date` מונע שתי
   רשומות באותו תאריך. אירוע יכול לחול על תאריך של שבת, ויכולים להיות שני
   אירועים באותו יום. הפתרון: אינדקס חלקי `where kind = 'shabbat'`.
2. **דליפת אירועים לרשימות שבת.** כל שאילתה שמושכת רשימת שבתות חייבת לסנן
   `kind='shabbat'`, אחרת אירוע יופיע ללקוח בטופס ההזמנה. רשימה מלאה בסעיף 8.

## 3. מיגרציות

### מיגרציה 52: `occasions_kind`

הפיכת `shabbatot` לטבלת מועדים.

```sql
alter table shabbatot
  add column kind text not null default 'shabbat',
  add column title text,                   -- שם האירוע (בשבת נשאר null)
  add column event_type text,              -- 'community' | 'private'
  add column event_time time,              -- שעת האירוע (אופציונלי)
  add column location text,                -- מקום האירוע
  add column use_full_workfile boolean not null default true;

alter table shabbatot
  add constraint chk_occasion_kind check (kind in ('shabbat', 'event')),
  add constraint chk_occasion_event_type
    check (event_type is null or event_type in ('community', 'private')),
  -- שבת חייבת פרשה; אירוע חייב שם
  add constraint chk_occasion_identity check (
    (kind = 'shabbat' and parasha is not null)
    or (kind = 'event' and title is not null and btrim(title) <> '')
  );

alter table shabbatot alter column parasha drop not null;
alter table shabbatot alter column hebrew_date drop not null;

-- תאריך ייחודי רק לשבתות; אירועים חופשיים
drop index uq_shabbatot_gregorian_date;
create unique index uq_shabbatot_gregorian_date
  on shabbatot (gregorian_date) where kind = 'shabbat';

create index idx_shabbatot_kind on shabbatot (kind);
```

`status` (`open`/`closed`/`completed`/`cancelled`) ו-`payment_deadline` מתאימים
כמות שהם גם לאירוע.

### מיגרציה 53: `order_inventory_lines`

שורות מלאי חופשיות בהזמנה. מזינות גם את התמחור וגם את צריכת המלאי.

```sql
create table order_inventory_lines (
  id                 uuid primary key default gen_random_uuid(),
  order_id           uuid not null references orders(id) on delete cascade,
  inventory_item_id  uuid not null references inventory_items(id),
  item_name_snapshot text not null,
  quantity           numeric(14,4) not null,
  unit_id            uuid references units(id),   -- יחידת ההזנה
  unit_cost          numeric(10,2) not null default 0,  -- עלות ליחידה, קפואה
  line_total         numeric(10,2) not null default 0,
  note               text,
  created_at         timestamptz not null default now(),
  constraint chk_order_inventory_lines_qty check (quantity > 0)
);

create index idx_order_inventory_lines_order on order_inventory_lines (order_id);
```

`unit_id` נשמר כדי שההמרה ליחידת הבסיס תעבור באותו מסלול של `recipe_lines`
(טבלת `inventory_unit_conversions`), כך שהעלות והניכוי לא יסטו זה מזה.

### מיגרציה 54: תמחור לפי עלות

```sql
alter table orders
  add column pricing_mode text not null default 'price_track',
  add column inventory_lines_amount numeric(10,2) not null default 0,
  add column base_amount_override numeric(10,2);

alter table orders
  add constraint chk_orders_pricing_mode
    check (pricing_mode in ('price_track', 'cost_based'));

alter table customers
  add column is_organization boolean not null default false;
```

- `pricing_mode` - `price_track` להזמנת שבת (ההתנהגות הקיימת), `cost_based` לאירוע.
- `inventory_lines_amount` - סכום השורות החופשיות, מרכיב נוסף בסכום הסופי.
- `base_amount_override` - "אפשרות התיקון". `null` = הסכום המחושב מהעלות.
- `is_organization` - משלם שאינו אדם פרטי (ועד הקהילה, גבאי, קרן). לא נכנס
  לרשימת הלקוחות בטופס ההזמנה ולא מתחבר למערכת.

**סעודת האירוע.** `order_meals` דורש `meal_slot_id`. במקום לשנות סכימה, המיגרציה
זורעת סעודת מערכת בשם "אירוע" עם `show_in_order_form = false` (הדגל ממיגרציה 46),
שמשמשת כברירת מחדל לאירועים. הכללים לפי קטגוריה (מינימום/מקסימום) לא נאכפים
במסלול האירוע. אירוע רב-סעודתי (שבע ברכות ליומיים) עובד מיד, כי המנגנון תומך
בכמה סעודות לאותה הזמנה.

## 4. שרת

### 4.1 שירות חדש: `services/costing.js`

חישוב עלות. מקור המחיר: `inventory_items.last_purchase_price` (מחיר בסיס לפני
מע"מ, לפי מיגרציה 33), פלוס מע"מ לפריט שאינו `vat_exempt`, לפי `vat_rate`
מ-`system_settings`.

```
mealCostPerPortion(meal)  =  Σ over recipe_lines:
    convertToBase(quantity_per_portion, unit_id, item)  ×  costPerBaseUnit(item)

eventCost(order) =
    Σ over order_meals:            mealCostPerPortion(meal) × portions
  + Σ over order_inventory_lines:  convertToBase(quantity, unit_id) × costPerBaseUnit
```

שתי נקודות קריטיות:

1. **אותו מסלול המרה בדיוק** כמו הניכוי. מייבא `convertRequirementsToBase`
   ו-`indexConversions` מ-`inventoryUnitConversion.js`. אם העלות והניכוי ישתמשו
   בהמרות שונות, המחיר לא ישקף את מה שירד מהמלאי.
2. **מחיר חסר אינו שגיאה חוסמת** אלא אזהרה מפורטת. פריט בלי
   `last_purchase_price` מוחזר ברשימת `missingPrices` והממשק מציג "העלות חלקית,
   חסר מחיר ל-X, Y". זו אותה תבנית שנעשית היום ב-`inventoryDeduction.js` עבור
   פקטור המרה חסר, רק שהמרה חסרה כן חוסמת ומחיר חסר לא.

הפונקציה גם מחזירה פירוט לכל מאכל, כדי שהמסך יראה "חזה עוף: 12.40 ש"ח למנה
× 80 מנות = 992 ש"ח" ולא רק סכום סופי.

### 4.2 עדכון `services/pricing.js`

`calcFinal` מקבל את `inventoryLinesAmount` כמרכיב נוסף:

```
final = base + extras + inventoryLines + manualCharges - discounts
```

כאשר `base` הוא `base_amount_override` אם הוגדר, אחרת הסכום המחושב.
התיקון הידני העדין יותר (הנחה, חיוב נוסף) ממשיך לעבור דרך `order_discounts`
ו-`order_manual_charges` הקיימות, שכבר מתועדות ומוצגות.

### 4.3 עדכון `services/inventoryDeduction.js`

ב-`collectConsumption` יש היום שני מקורות צריכה: מאכלים (מכפיל = מנות) ותוספות
בתשלום (מכפיל = יחידות חיוב). נוסף **מקור שלישי**: `order_inventory_lines`,
עם מכפיל 1 כי הכמות מוחלטת ולא פר-מנה.

השינוי מקומי: הוספת `order_inventory_lines (inventory_item_id, quantity, unit_id)`
ל-`select` של ההזמנות, ולולאה אחת נוספת ל-`addLine`. ה-RPC לא משתנה.

### 4.4 עדכון `services/shabbatFile.js`

אותה תוספת ב-`buildInventoryReport` (דוח חוסרים) וב-`buildKitchen`, כדי ששורות
חופשיות ייכללו בדוח החוסרים וברכש הישיר. `isOperational` נשאר כפי שהוא: אירוע
נכנס לחישוב כשהוא מאושר, בדיוק כמו הזמנת שבת (כלל 8.7).

### 4.5 ראוט חדש: `routes/events.js` (מאחורי `requireAdmin`)

| נתיב | תפקיד |
|---|---|
| `GET /` | רשימת אירועים (`kind='event'`) עם סיכום: מנות, סכום, שולם, יתרה |
| `POST /` | יצירת אירוע: רשומת מועד + `shabbat_files` + הזמנה אחת |
| `GET /:id` | אירוע מלא: מועד, הזמנה, מאכלים, שורות חופשיות, עלות, תשלומים |
| `PATCH /:id` | עדכון כותרת, תאריך, סוג, מקום, מועד תשלום, סטטוס |
| `PUT /:id/menu` | החלפת התפריט: מאכלים + שורות חופשיות, ואז חישוב מחדש |
| `POST /:id/recalc-price` | חישוב עלות מחדש לפי המחירים העדכניים |
| `POST /:id/promote` | `use_full_workfile = true`, מחזיר קישור לתיק המלא |
| `DELETE /:id` | מחיקה (רק `developer`, כמו מחיקת תיק שבת) |

`POST /` יוצר את שלושת הרכיבים בזה אחר זה. אין טרנזקציה בין קריאות Supabase,
לכן כישלון באמצע צריך ניקוי מפורש (מחיקת המועד שנוצר), כמו שנעשה היום
ב-`shabbatFile.js`.

**גבייה: אפס קוד חדש.** `routes/payments.js` עובד לפי `order_id`, ולכן הנתיבים
`/orders/:id/payments` וההחזרים עובדים לאירוע כמות שהם.

### 4.6 עדכון `routes/finance.js`

- התווית של הכנסה היום היא `shabbatot.parasha`. משנים ל-`coalesce(title, parasha)`
  ומוסיפים `kind` לבחירה, כדי להציג "אירוע: בר מצווה כהן" ולא מקף.
- פילוח נוסף: `income.by_kind` עם הפרדה בין שבתות לאירועים, ובתוך האירועים בין
  `community` ל-`private`. זו הסיבה העיקרית לתיוג.
- שאר החישובים (חובות לקוחות, יתרה פתוחה, הכנסות מול הוצאות) קולטים את האירועים
  אוטומטית, כי הם נשענים על `orders` בלי סינון לפי סוג המועד.

## 5. לקוח

### 5.1 מסך `/admin/events` (חדש)

`DataTable` בקונבנציה הקיימת של הפרויקט (סינון פר-עמודה, מיון בלחיצה) עם
`Drawer` לפתיחת רשומה, בדיוק כמו `AdminSuppliers` ו-`AdminInventory`.

עמודות: תאריך, שם האירוע, סוג (פנימי/פרטי), משלם, מנות, סכום, שולם, יתרה,
סטטוס תשלום, האם המלאי נוכה.

### 5.2 עורך האירוע (בתוך ה-Drawer)

ארבעה חלקים:

1. **פרטי האירוע** - שם, תאריך, שעה, מקום, סוג, משלם, מועד אחרון לתשלום.
   בורר המשלם מציג לקוחות רגילים וארגונים יחד, עם כפתור "משלם חדש" שיוצר
   רשומת לקוח (ולארגון מסמן `is_organization`).
2. **תפריט** - שתי לשוניות:
   - *מאכלים מהקטלוג*: בורר בסגנון `MealCategoryPicker` הקיים, בלי אכיפת
     מינימום/מקסימום, עם שדה מנות.
   - *שורות חופשיות*: בורר פריט מלאי + כמות + יחידה, עם המחיר האחרון כברירת
     מחדל. אותו רכיב בורר יחידות שמשמש במלאי (טבלת `units` ממיגרציה 36).
3. **תמחור** - פירוט העלות המחושבת שורה-שורה, הסכום המחושב, שדה עקיפה
   (`base_amount_override`), והנחות/חיובים ידניים דרך הרכיבים הקיימים
   מ-`AdminOrderEdit`. אזהרה בולטת אם חסרים מחירי עלות.
4. **גבייה ומלאי** - רכיב התשלומים הקיים מ-`AdminOrderView` בלי שינוי, לצד
   תצוגה מקדימה של צריכת המלאי וכפתור "נכה מלאי" שקורא לנתיב הקיים
   `POST /api/admin/inventory/shabbat/:id/deduct-auto`.

בראש העורך כפתור **"הפוך למועד מלא"** שקורא ל-`POST /:id/promote` ומנווט
ל-`/admin/shabbat-files/:id`, שם נפתחות כל הלשוניות: מטבח, אריזה, שינוע,
מתנדבים, חוסרים, הדפסות.

### 5.3 שינויים במסכים קיימים

- `ShabbatFiles` - סינון `kind='shabbat'`, פלוס לשונית/מסנן להצגת אירועים
  שקודמו למועד מלא.
- `ShabbatFile` - כותרת המסך מציגה `title` לאירוע במקום פרשה.
- `AdminFinance` - כרטיס "הכנסות מאירועים" עם הפילוח החדש.
- `AdminOrders` - עמודת "מועד" תציג את שם האירוע; מסנן להסתרת אירועים.
- ניווט - פריט "אירועים" בסרגל הצד.

## 6. שלבי ביצוע

השלבים בנויים כך שכל אחד מהם ניתן לבדיקה בפני עצמו.

### שלב 1: תשתית המועדים (מיגרציה 52 + סינון)

מיגרציה 52, ואז סגירת כל נקודות הדליפה. זהו השלב הרגיש ביותר כי הוא נוגע בקוד
קיים ופעיל. בסופו המערכת מתנהגת בדיוק כמו קודם, וזו בדיקת הקבלה: יצירת רשומת
`kind='event'` ידנית ב-DB לא משנה שום מסך קיים.

### שלב 2: תמחור לפי עלות (מיגרציה 54 + `costing.js`)

השירות והבדיקות שלו, לפני שיש בכלל ממשק. ניתן לאמת מול מאכל אמיתי מהקטלוג
ולהשוות ידנית מול המתכון והמחירים.

### שלב 3: שורות מלאי חופשיות (מיגרציה 53)

הטבלה, שילובה ב-`inventoryDeduction.js` וב-`shabbatFile.js`. בדיקה: הזמנת שבת
קיימת עם שורה חופשית מנוכה נכון ומופיעה בדוח החוסרים.

### שלב 4: שרת האירועים (`routes/events.js`)

כל הנתיבים, כולל `promote`. בדיקה מקצה לקצה ב-API לפני שנכתב ממשק.

### שלב 5: מסך האירועים

הטבלה והעורך על כל ארבעת חלקיו.

### שלב 6: אינטגרציה כספית ותיעוד

`finance.js`, `AdminFinance`, ועדכון `docs/מדריך-למשתמש.md` ו-`AdminGuide`.

## 7. סיכונים ונקודות תשומת לב

**דליפת אירועים לממשק הלקוח.** הסיכון החמור ביותר: אירוע פרטי שמופיע לכל
הקהילה בטופס ההזמנה. הסינון בשלב 1 חייב להיות מלא, ורצוי בדיקה אוטומטית אחת
שמוודאת ש-`GET /api/shabbatot/open` לא מחזיר אירועים.

**מיגרציות שטרם הורצו ב-DB.** לפי הזיכרון, מיגרציות 39, 40, 43, 44, 45, 46 ואולי
נוספות טרם הוחלו על מסד הנתונים החי. מיגרציה 54 נשענת על `show_in_order_form`
ממיגרציה 46. יש לוודא סנכרון מלא לפני ההרצה.

**עלות אינה מחיר.** תמחור לפי עלות מוצרים לא מכסה תקורה, עבודה, גז, אריזה או
בלאי. `base_amount_override` והחיובים הידניים פותרים את זה נקודתית. אם יתברר
שנדרשת תוספת קבועה, `cost_markup_percent` ברמת האירוע היא הרחבה קטנה בהמשך.

**עלות משתנה בזמן.** המחיר מחושב מ-`last_purchase_price` הנוכחי. אם המחיר
מתעדכן אחרי שהאירוע תומחר, הסכום השמור בהזמנה לא זז, וזה הנכון (עיקרון המחירים
הקפואים, סעיף 15.3). כפתור "חשב מחיר מחדש" קיים למי שרוצה לרענן במפורש.

**עקביות מלאי מול תמחור.** אם פריט חסר פקטור המרה, הניכוי נחסם והתמחור עדיין
יעבוד חלקית. יש להציג את שתי האזהרות באותו מקום בעורך.

## 9. מה נבנה בפועל

כל ששת השלבים מומשו. הבנייה הלכה אחרי התוכנית, עם שלוש סטיות מכוונות שמתועדות למטה.

### מיגרציות

| קובץ | תוכן |
|---|---|
| `00000000000052_occasions_kind.sql` | `kind`, `title`, `event_type`, `event_time`, `use_full_workfile` ל-`shabbatot`; `parasha`/`hebrew_date` הפכו ל-nullable עם אילוץ זהות מותנה; האינדקס הייחודי על התאריך הפך חלקי (`where kind = 'shabbat'`) |
| `00000000000053_order_inventory_lines.sql` | טבלת שורות המלאי החופשיות |
| `00000000000054_event_cost_pricing.sql` | `pricing_mode`, `inventory_lines_amount`, `base_amount_override` ל-`orders`; `is_organization` ל-`customers`; זריעת סעודת "אירוע" |

### שרת

- `services/costing.js` - חישוב עלות מהמתכונים ומהמחיר האחרון, כולל מע"מ לפי הפטור הפר-פריטי.
- `lib/costMath.js` - חשבון העלות הטהור, בלי גישה למסד.
- `routes/events.js` - כל נתיבי האירועים, כולל `promote`.
- שולבו שורות המלאי החופשיות ב-`inventoryDeduction.js` וב-`shabbatFile.js` (ניכוי ודוח חוסרים).
- `finance.js` - פילוח `income.by_kind` והתוויות של אירועים.
- סינון `kind='shabbat'` נסגר בכל ששת מקומות הרשימה מסעיף 8, ובנוסף נחסמה יצירת הזמנת לקוח על מזהה של אירוע ב-`orders.js`.

### לקוח

- `pages/AdminEvents.jsx` - הטבלה והעורך על חמש לשוניותיו (תפריט, תמחור, גבייה, מלאי, פרטים).
- `occasionLabel()` ב-`status.jsx` ו-`formatShabbatTitle()` ב-`dates.js` - מקור אמת אחד לתווית מועד, מוחל על כל המסכים שהציגו `parasha` ישירות.
- ניווט: פריט "אירועים" בקבוצת "הזמנות ומועדים".

### בדיקות

`test/costMath.test.js` - 5 בדיקות על חשבון העלות: תוספת מע"מ, פטור, מחיר חסר שמחזיר `null` ולא אפס, ופקטור המרה חסר שאינו מומצא. סך הבדיקות בשרת: 20, כולן עוברות. בניית הלקוח עוברת.

### סטיות מהתוכנית

**אין עמודת `location` ב-`shabbatot`.** מקום האירוע יושב על ההזמנה
(`venue_name`/`venue_address`), שם הוא ממילא שדה חובה לפי מיגרציה 27 ומשם קורא
אותו דוח השינוע. עמודה נוספת הייתה מקור אמת שני לאותו נתון.

**תיק העבודה נוצר תמיד, כבר ביצירת האירוע.** התוכנית השאירה פתוח מתי הוא נוצר.
ה-RPC של ניכוי המלאי דורש רשומת `shabbat_files` ומשתמש ב-`is_inventory_deducted`
שלה כהגנה מפני ניכוי כפול, ולכן יצירה מיידית נותנת ניכוי מלאי לאירוע "קל" בלי
לשנות את ה-RPC. `use_full_workfile` נשאר מתג תצוגה בלבד.

**`cost_markup_percent` לא נבנה.** התיקון הידני נעשה דרך `base_amount_override`
וההנחות/חיובים הקיימים, כפי שהתוכנית העדיפה. אם יתברר שמוסיפים אחוז קבוע בכל
אירוע, זו הרחבה קטנה.

### מה נשאר פתוח

- הרצת שלוש המיגרציות על מסד הנתונים החי.
- הזמנת רכש עדיין נקשרת לשבת בלבד בממשק (`AdminPurchaseOrders`); לאירוע אפשר
  לייצר רכש דרך דוח החוסרים, אך לא לבחור אותו בבורר המועד.
- `docs/מדריך-למשתמש.md` ומסך `AdminGuide` טרם עודכנו.

## 10. תוספת: קישור אירוע פרטי לשבת קיימת (מיגרציה 60, 2026-08-20)

אירוע פרטי (למשל קידוש בר מצווה) שחל בפועל בזמן שבת קהילתית קיימת לא היה אמור
לקבל תיק עבודה מקביל משלו - הוא צריך להיכנס לאותו תיק עבודה, אותו ניכוי מלאי
ואותו מטבח. עד כה כל אירוע יצר מועד עצמאי (`shabbatot` בסוג `'event'`) בלי
יוצא מן הכלל.

**הפתרון: חיבור מלא, לא תיוג בלבד.** הזמנת אירוע פרטי מקושר אינה יוצרת
`shabbatot`/`shabbat_files` חדשים בכלל - היא מצביעה ישירות דרך `orders.shabbat_id`
על השבת האמיתית הקיימת (`kind='shabbat'`), עם `pricing_mode='cost_based'` בדיוק
כמו אירוע עצמאי. השילוב הזה - `pricing_mode='cost_based'` על הזמנה ששייכת
ל-`shabbatot.kind='shabbat'` - הוא הזיהוי היחיד הדרוש ל"אירוע פרטי מקושר"; אין
דגל נפרד.

מכיוון שרשומת המועד משותפת עם השבת האמיתית, שם/שעת האירוע לא יכולים לשבת עליה
(זה היה "מזהם" אותה לכל שאר הזמנות אותה שבת). מיגרציה 60 מוסיפה
`orders.event_title` ו-`orders.event_time`. הערות האירוע המקושר משתמשות
בעמודה הגנרית `orders.notes` (מיגרציה 48) שכבר קיימת.

### שרת (`routes/events.js`)

- `loadEvent(id)` מתפצל לשני תרחישים: אם `id` הוא `shabbatot` מסוג `'event'` -
  עצמאי, כמו קודם. אחרת מנסה `id` כמזהה הזמנה עם `pricing_mode='cost_based'`
  ו-`order_kind='occasion'`, וטוען את השבת שהיא מצביעה עליה (`kind='shabbat'`).
  **:id של אירוע מקושר הוא מזהה ההזמנה עצמה**, כי `shabbat_id` משותף עם הזמנות
  נוספות ואינו מזהה ייחודי לאירוע.
- `normalizedOccasion()` בונה אובייקט "מועד" אחיד לתצוגה: לאירוע מקושר, שם/סוג/
  שעה מגיעים מההזמנה ולא מ-`shabbatot`.
- `GET /` ממזג שתי שאילתות: `shabbatot` בסוג `'event'` (כרגיל) + `orders` עם
  `pricing_mode='cost_based'` שמצביעות על `shabbatot.kind='shabbat'` (חדש,
  `shabbatot!inner` לסינון לפי הטבלה המקושרת).
- `POST /` מקבל `link_to_shabbat_id` אופציונלי, מותר רק כש-`event_type='private'`.
  כשהוא קיים: מוודא שהשבת קיימת, `ensureShabbatFile` (הגנה - כבר קיים בפועל),
  ויוצר רק הזמנה.
- `PATCH /:id` מפצל בין שני מסלולי שדות: מקושר כותב `title`/`event_time`/`notes`
  להזמנה בלבד; תאריך/סטטוס/מועד תשלום שייכים לשבת המשותפת ואינם ניתנים לעריכה
  מכאן (עריכתם דרך תיק השבת).
- `POST /:id/promote` הופך ל-no-op לאירוע מקושר (`use_full_workfile` כבר `true`
  תמיד, כי מדובר בתיק עבודה אמיתי וקיים).
- `POST /:id/link-to-shabbat` (2026-08-20) - קישור בדיעבד של אירוע עצמאי
  **קיים** לשבת קיימת, בלי לאבד את התפריט/התמחור/התשלומים שכבר הוזנו (הם
  תלויים ב-`order_id` ולא נוגעים בשינוי). מותר רק ל-`event_type='private'`
  שאינו מקושר כבר, וחסום אם `shabbat_files.is_inventory_deducted` - התנועות
  כבר נרשמו על ה-`shabbat_id` הישן ולא ניתן "לנייד" אותן. מעדכן את ההזמנה
  (`shabbat_id`, `event_title`, `event_time`, `notes`) ואז מוחק את המועד ותיק
  העבודה העצמאיים שהתייתמו - אותו דפוס מחיקה כמו `DELETE /:id`.
- `DELETE /:id` לאירוע מקושר מוחק **רק** את ההזמנה ומה שתלוי בה
  (`customer_payments`, `order_refunds`) - **לא** את `shabbat_files`/`shabbatot`
  ו-**לא** את `inventory_movements`, ששייכים לצריכה המצטברת של כל השבת ולא
  להזמנה בודדת (`deduct_shabbat_inventory` הוא RPC ברמת שבת, לא ברמת הזמנה).

### כספים (`routes/finance.js`)

`isEvent`/`kindKey` הישן הסתמך רק על `shabbatot.kind==='event'`, ולכן אירוע
פרטי מקושר היה נספר בטעות תחת "שבתות". הוחלף ב-`orderEventType(o)`: אירוע
עצמאי לפי `shabbatot.kind`, אירוע מקושר לפי `pricing_mode==='cost_based'` על
הזמנה ששייכת לשבת אמיתית. `orderOccasionLabel(o)` מציג `"<פרשה> · <שם האירוע>"`
לחוב לקוח של הזמנה מקושרת, כדי להבדיל אותה מהזמנות הקהילה הרגילות של אותה שבת.

### לקוח (`AdminEvents.jsx`)

- הטבלה מציגה שני סוגי שורות יחד: אירועים עצמאיים (מ-`shabbatot`) ואירועים
  מקושרים (מ-`orders`), עם badge "משויך לשבת" לזיהוי.
- טופס היצירה: כשסוג האירוע `'private'`, נפתח בורר "קישור לשבת קיימת"
  (`api.allShabbatot()`) שכשנבחר מסתיר תאריך/מועד תשלום (יורשים מהשבת).
- כל קריאות ה-API בכרטיס האירוע (תפריט/תמחור/פרטים/מחיקה/קידום) עברו משימוש
  ב-`event.id` (מזהה המועד) לשימוש ב-`id` המנורמל שמחזיר השרת (`routeId`),
  כי לאירוע מקושר אלה שני מזהים שונים. `event.id` נשאר לניווט לתיק השבת בלבד.
- לשונית מלאי לאירוע מקושר מחליפה את כפתור "ניכוי מלאי" (שהיה מנכה את **כל**
  השבת בטרם עת) בהודעה + קישור לתיק השבת עצמו.
- לשונית פרטים מסתירה תאריך/סטטוס/מועד תשלום לאירוע מקושר, ומציגה הערה
  שהם נקבעים לפי השבת.
- לשונית פרטים של אירוע עצמאי מסוג `'private'` מציגה גם `LinkToShabbatPanel` -
  כפתור "קישור לשבת קיימת" שפותח בורר שבת וקורא ל-`POST /:id/link-to-shabbat`.
  אחרי קישור מוצלח המזהה של האירוע מתחלף (מ-`shabbatot.id` ל-`order.id`),
  ולכן `AdminEvents` מקבל callback ייעודי (`afterLink`) שפותח מחדש את הכרטיס
  עם המזהה החדש במקום לרענן עם המזהה הישן שכבר לא קיים.

### מה נשאר פתוח

- הרצת מיגרציה 60 על מסד הנתונים החי.
- אין בדיקה אוטומטית ייעודית לתרחיש המקושר (הבדיקות הקיימות הן ברמת שירות
  טהור ולא נוגעות ב-routes/events.js); אומת רק build+syntax, לא end-to-end
  מול DB חי.
